# SHRINK: can the 7 VSS worlds be smaller? (2026-11-02)

Owner's question: "can they be smaller?". The 7 worlds of the default composer (`docs/model/micro/registry.json`: shapes7c, links7,
position7, questions7, graphq7, manage7, history7) are 35.57 MB on disk (BUILD.json left out), plus 2.38 MB of cutters (cutter_worlds7s,
cutter_events): 37.95 MB downloaded by the demo.

| file (7 worlds together) | MB | what it is |
|---|---|---|
| stars.bin | 18.81 | 18,144 word / role / operator vectors, 8-bit phases, D 1024 (1 KB each) |
| routebook.bin | 15.83 | the learned phases (path, bg0 dense; bg, A, L sparse: trained rows only), 8 bits |
| model.json, front.json, manifest.json | 0.93 | |

No model was trained. Nothing under `docs/model/` was changed: the candidate exports are outside the repository (below).

## 1. Stars: generated in the browser, byte for byte (adoptable)

What stars.bin holds: for every key the reader can ask for (`export_web.star_keys`: `id:<word>` of every catalog word, lexicon word, legend
verb and lemma; `role:<r>` of the 27 roles; 14 `op:` decoder operators; `marker`), the star_version 2 vector (SHA-256(`seed:name`) ->
xoshiro128**, the function docs/js/vss/stars.js already has), its phases **quantized to 8 bits**. No identity_table, no star_table (all 7
worlds: catalog star_version 2, identity_table false). A word outside the keys is already generated by the browser, unquantized.

Found: regenerating each key's star and quantizing it exactly as export_web.py quantizes (q = round((phase + pi) / 2pi * 256) mod 256,
computed on the generator's integer as floor((u + 2^23) / 2^24) mod 256: the phase 2pi (u + 0.5) / 2^32 - pi never sits on a rounding
boundary) gives **every byte of all 7 stars.bin files** (18,144 stars x 1024 bytes, 0 differences; checked in Python by
`export-web --from-web --stars generated` and in JS by `test_generated_stars.mjs`: the dequantized float64 values are `===` equal).
So the browser can generate them instead of downloading them, with the same numbers and therefore the same decisions.

Format **vss-web-3** (manifest `"format": "vss-web-3"`, `"stars": {"source": "generated", "file": "stars.json", "bits": 8, "quantize": "keys"}`):
no stars.bin; `stars.json` lists the keys (0.23 MB for the 7 worlds) and the bits. `loader.js` builds a `GeneratedStars` table: a key's
star is generated and quantized on its first use (nothing at load); words outside the keys stay unquantized, as before. Old exports
(vss-web-1 / vss-web-2, stars.bin) load through the unchanged path: the shipped worlds give the same decisions with the new code on all
1000 sample messages (produced requests, confidences, gated tallies), and `regress.sh` (run step by step, one node process at a time) gives
the table below.

Measured with the candidate `gen8` (the 7 worlds converted by `sop export-web --from-web <world> --out <dir> --stars generated`):
- sample (1000 messages, 4858 requests) and fresh2 (600 messages, 1909 requests): **0 messages changed**, 0 confidence differences, 0
  execute / ask changes at 97%;
- the short sets (`short_bench.mjs`, GATE=97): the per-row output file is byte-identical to the shipped worlds';
- `test_vss_confidence.mjs` (REGISTRY=gen8): PASS, confidence difference 0, 0 of 302 decisions differ at every level.

Shared stars file (the fallback asked for): the worlds share the seeds (seed 0, star seed `sop-stars-v1`), so equal keys are equal stars
(no conflict found); the union is 6,919 stars = 7.1 MB instead of 18.8 MB. Not needed: generation removes all 18.8 MB.

Float stars (no quantization, `sfloat`, an experiment): 5 sample messages change, 1 request (right +1, wrong -1); 2 fresh2 messages, no
request outcome; 1 execute / ask decision changes on fresh2. So the 8-bit stars are not "worse" than the exact ones; they are just
different numbers, and generation reproduces them exactly instead.

- Stars and route book lose about the same at 2 and 1 bits (sample requests changed: s2 59 vs rb2 67, s1 234 vs rb1 206; together

## 4. D = 512: needs retraining, not run here (a later experiment)

Evidence available:
- This repository, INTERFERENCE.md (one world, comb1 settings, SEG=gold, wires right): D 512 / 1024 / 2048 fit 68.5 / 68.8 / 69.5%, dev
  66.5 / 65.5 / 66.3%. Halving D did not lose wires right on that model (one seed each).
- vsa-semantic-space RESULTS J1 (identity capacity, D 256 / 512 / 1024): 8 identities .85 / .95 / .97; 24 identities .61 / .74 / .83;
  64 identities .45 / .56 / .66: D 512 loses 2-10 points as the number of identities grows.
- RESULTS 13 (B6), synthetic capacity at D 1024: 32 bundled role-filler terms read back clean, 64 begin to fail. Capacity scales with D,
  so about 16 clean and 32 failing at D 512. Our requests: median 6 tokens (p90 9-10) per gold span on the sample and fresh2, 3 codes per
  token (path, chainL, bigram): about 18 terms (p90 27-30). At D 1024 they sit well inside the clean range; at D 512 the median is at the
  edge and the long requests beyond it.
- RESULTS 10b-ter: D 2048 vs 1024 did not repair depth-3 readings (0.852 vs 0.813, within seed noise): more D is not what limits there.

Estimate: D 512 halves the route book (15.8 -> 7.9 MB at 8 bits, 4.0 MB at 4 bits) and the compute; the wires right should stay within
about a point (INTERFERENCE.md), but the margins shrink (noise per term ~ 1/sqrt(D) grows by 1.41), so the confidence spreads less and
more requests would be asked, mostly the long ones; the cost score is the measure that can show it. Not adopted without a training.

Later experiment (written for the owner, not run): retrain the 7 worlds at D 512 (`D=512` in train_micro.sh, FAST=1 of FAST_TRAIN.md,
same data and seed 0), export with gen8 stars, refit nothing else; measure on the fresh2 test part the cost score at the demo's threshold
and at the calibration-chosen threshold, the confidently-wrong rate, right %, per request length (<= 6 tokens, 7-10, > 10); adopted only
if the cost score stays within the bootstrap interval of today's (COST_SCORE.md) and the long requests lose no more than the interval.

## How to adopt gen8 (the coordinator's decision; nothing under docs/model was changed)

For each world: `training/vss/tool/bin/sop export-web --from-web docs/model/micro/<w> --out <tmp>/<w> --stars generated` (refuses if any
star differs), then replace the folder's stars.bin and manifest.json by the new stars.json and manifest.json (model.json, routebook.bin,
front.json are byte-identical copies), run `python3 training/sketch/stamp_models.py` (the folder versions change; stamp_models needs no
change: it hashes whatever files the folder has) and regress.sh. New trainings: add `--stars generated` to the export line of
train_micro.sh (not changed here). Also to update when adopted: `VSS_HINT` in docs/js/ui.js (38.0e6 -> about 19.4e6) and the file lists
in docs/js/docs-arch.js; training/sketch/parity_reader.py reads stars.bin directly: `export_web.stars_of_web(dir)` returns the same
(keys, phases) for both formats.
