What is evaluated today, and what should count as faithful SOP?

Today the main score compares predicted SOP nodes against annotated action/argument records. The comparison is deterministic, but it is lossy and mixes some reader and context decisions. It does not yet establish complete frame fidelity.

Evaluate the intended semantic frame before context resolution, then evaluate symbolic execution separately.

The direct answer

Yes: the principal comparison is based on SOP meaning, represented as actions and arguments. It is not an LLM assigning a subjective grade to the answer, and it is not the VSS training cosine. The expected answer is usually stored in JSON as type, args and a source span. The reader returns SOP nodes. Code converts both into comparable maps and counts matching requests.

But it is not a strict semantic-frame comparison. The code removes some fields and distinctions, uses a one-sided argument check and, in some paths, matches requests by the values that agree best. Some pipelines also fill references from context before scoring. A separate scene report compares executed drawings with geometric tolerances. These choices must not all be described as “the reader understood the text”.

The frame, not a drawing or a natural-language answer, is the reader’s deliverable. A later agent or symbolic engine should mechanically inspect the operation, resolve references if it can, choose permitted defaults, dispatch the right code and ask when a required value remains unresolved.

One message through the existing main scorer

Make Box red.

Faithful SOP frame:

@c1 command action=set target=Box color=red

In the annotation file, the same expectation can be stored as follows. The fact that it is JSON rather than a .sop string is not a problem: both can describe the same typed node.

{
  "text": "Make Box red.",
  "wires": [{
    "span": "Make Box red",
    "type": "command",
    "args": {"action": "set", "target": "Box", "color": "red"}
  }]
}

llm_score.mjs takes the reader nodes, removes mention nodes from the action count, and uses canon() to turn each main node into a map. References to mention nodes are folded into descriptive strings. The annotation takes the corresponding canonWant() path. The evaluator then associates produced actions with expected actions.

By default, association uses an ordered longest-common-subsequence match on type plus action/ask. With PAIR=value, it groups by action and finds a weighted matching that prioritizes matching argument values, then overlap with the annotated text span. For each associated pair, scoreMessage() checks every gold key. If those keys match, the pair is right. Otherwise it is wrong-aligned. Unpaired expected actions are missed; unpaired predictions are extras.

A wrong action type can therefore appear as a missed expected action plus an extra predicted action, rather than as a wrong-aligned pair. The report’s categories need to be read with this matching rule in mind. The main totals are per requested action, not “whole message perfect”.

Not all normalization is a strange heuristic. Argument-key order is irrelevant. Internal wire IDs can be renamed consistently. Some operations are symmetric under the engine’s contract. The problem is granting equivalence without preserving the distinctions that the user supplied. Keep a small, documented list of valid equivalences and test both accepted and rejected cases.

Other numbers in the repository answer different questions

Training losses and head/tag accuracy show what the optimizer fits. VSS cosine measures a vector objective. SOP-BERT cross-entropy and per-key/tag checks measure class and token decisions. These are useful diagnostics but not the same as a faithful emitted frame. SOP-BERT’s internal request score also tolerates extra predicted fields in the inspected code. The shipped --all schedule keeps its final epoch rather than choosing one by that held-out score.

Target round trips ask whether annotated meaning survives conversion into the training/output format and back. A failure here can occur without any prediction error. It must be repaired or explicitly represented before a low model score is attributed to learning capacity.

Confidence reports use right/wrong labels for predicted requests and a threshold that selects what is executed. Their headline precision is right/(right+wrong+extras) among executed requests; useful coverage is right/requested. The project’s utility is 100×(right−10×(wrong+extras))/requested. A held request scores zero. These numbers inherit the semantic-comparison labels. The offline gated path also documents an all-executed-context approximation.

Scene replay adds the symbolic engine and compares resulting shapes, links and groups. In scene_readers.mjs, the default position/size tolerance is 12 pixels. If a name is missing, a same-shape object within 40 pixels can be associated as a renamed counterpart; the name difference is still reported. This helps diagnose application output. It is not an appropriate tolerance for reading the explicit number 400 as 412, and it cannot tell by itself whether the reader or resolver caused a difference.

Where human judgment enters, and how to constrain it

The matching code is deterministic: given the same nodes and configuration it gives the same result. The reference annotation is where interpretation enters. “Make Box red” has little room for disagreement. “Make it larger”, an implicit create, a correction or a genuinely ambiguous phrase may require a stated convention, alternatives, or an unresolved field. An annotation that fills an exact amount or object without textual support is not made objective by being called gold.

Use literal source spans for explicit values. Record which fields are stated, which are unresolved and which are executor defaults. Allow genuinely equivalent frame graphs. Review annotation disagreements separately from reader mistakes. Report how many cases are ambiguous or disputed instead of hiding them inside an accuracy percentage. I cannot quantify annotation subjectivity from code inspection alone; that requires a reviewed sample and disagreement counts.

Do not demand pronoun resolution to prove that the reader understood “it”. Do not accept a guessed target merely because it happened to produce a plausible drawing. The reader-level reference should preserve the expression and its role; a resolver-level reference can separately state the intended entity for a fully specified scene.

The proposed evaluator: a semantic contract before execution

Keep the original text and annotate an ordered graph of requested events, argument values, source spans, cross-event references and explicit unresolved roles. Store the accepted semantic alternatives when a sentence supports more than one. Parse the reader’s SOP into the same graph. Compare graphs up to internal ID renaming and documented semantic equivalences, preserving explicit numbers, literals, target identity and required dependencies.

Each assertion in a produced frame should have a traceable origin. Compare the union of asserted fields, so an extra shape is detected. Distinguish a field not stated by the user from a field stated but not read. Associate events with their source occurrence and dependency relations; do not let a best-value match erase a reversal or a duplicated action. Multiple events may share a span, as in “a red square and a blue circle”, so source spans alone are not unique event IDs.

The output schema must represent a reference separately from a resolved entity. One possible extension is shown below. This is a proposed SOP construct, not syntax supported by the current engine; its purpose is to make the required distinction concrete.

# Proposed interface extension; do not execute in the current engine.
@r1 reference kind=pronoun text="it"
@c1 command action=move target=$r1 direction=left distance=20

A less intrusive option is a valid partial SOP program accompanied by typed unresolved-role metadata and source spans. Either design must stop the consumer from treating an unresolved mandatory role as an absent optional one. The schema decision should be explicit before implementation.

Keep the current execution-risk report as the second stage. First report reader fidelity and completeness, including false assertions and extras at each confidence threshold; then run the resolver/executor and attribute additional failures to those stages. A final drawing should illustrate what the complete system does, not decide whether a pronoun-preserving reader was truthful.

Implementation order: write the acceptance cases above, repair canonicalization and field comparison, define the unresolved-role contract, update labels, then refit confidence and rerun existing evaluations with root-cause analysis. Compare old and repaired counts on the same saved outputs before retraining any model. These changes are proposed here; this documentation task does not alter scoring or reader behavior.
