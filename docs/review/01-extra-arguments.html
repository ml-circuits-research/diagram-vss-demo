01 / measurement

An extra SOP argument is an extra assertion about the request.

The reader must preserve what the person said. Returning the requested color does not make the frame correct if it also asserts an unrequested shape change.

Compare the meaning of every produced argument, including arguments absent from the reference.

The concrete case: change the color of Box

Make Box red.

Faithful SOP frame:

@c1 command action=set target=Box color=red

The different frame discussed below:

@c1 command action=set target=Box color=red shape=circle

The first frame gives a symbolic system enough information to call its color-setting operation. It leaves the existing shape alone. The second frame also asks the executor to change the shape to a circle. That additional instruction is not supported by the sentence. The reader has invented part of the intent, even though its action, target and color are correct.

No pronoun resolution or knowledge of the drawing is needed to identify the difference. The target is explicitly Box. Whether Box currently exists is a later symbolic check. Even if Box happens to be a circle already, the second frame still contains an unsupported assertion: a future executor must not rely on a lucky current state to excuse the reader.

This example uses supplied frames to inspect the evaluator. It is not a claim that a particular trained model produced this exact sentence/frame pair.

Why the current comparison accepts the extra field

In scoreMessage(), the reference becomes a map of expected arguments. The code iterates over that map and checks whether each expected value appears in the prediction. All three expected values match in this example. There is no second check for a predicted field that the reference does not contain, so shape=circle is ignored. The separate count of extra actions does not help: the unwanted assertion is inside the existing action.

The same definition of right/wrong is used to prepare confidence labels in collect_pair.mjs. SOP-BERT’s internal evaluation also records extra fields without making the request incorrect. This is therefore more than a reporting cosmetic: a confidence fit can learn that a semantically wrong frame is a successful reading.

The correction and the exact acceptance condition

The evaluator should compare the complete typed frame: the operation, all explicit arguments, references between nodes and the status of unresolved fields. For each argument present on either side, it must decide whether the prediction preserves the reference meaning. A missing explicit color, a changed color and an invented shape are different diagnostics, but none is a faithful complete reading of this request.

This does not mean adding every drawing default to the reference. If the user did not choose a size, the reader should not be required to invent one. Defaults belong to the symbolic executor. If an existing adapter inserts a default, the evaluation record needs to retain that origin so a default is not misrepresented as text-derived intent.

The minimal check is mechanical: the first frame above passes; the second fails with “unsupported argument: shape.” Changing the current drawing must not change that judgment. A recorded uncertainty about a field is kept as uncertainty and contributes to incomplete coverage, rather than becoming an invented value. Only after these labels are corrected should confidence be refitted.

Established: the extra-field acceptance was reproduced, and the comparison is visible in the code. Unknown: its frequency in real outputs and the change in the models’ ranking after correction. The evaluation walkthrough explains the proposed reader-level contract in full.
