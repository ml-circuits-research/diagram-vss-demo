The evaluator removes distinctions that a symbolic program needs.

Normalization is useful for harmless differences in notation. It becomes a bug when it removes an explicit amount, an entity identity, literal text or a dependency between operations.

Canonicalize notation; preserve the semantic distinctions that the text supplied.

An explicit factor must survive comparison

Resize Box by a factor of 2.

Faithful SOP frame:

@c1 command action=resize target=Box scale=2

The different frame discussed below:

@c1 command action=resize target=Box scale=0.5

These frames request opposite changes. A symbolic executor can multiply the size by 2 or by 0.5 without interpreting English. That is exactly the division of work the technology should enable. The current canonicalizer drops scale from both frames, so the evaluator sees the same action and target and can accept the second frame.

The source comment justifies ignoring scale because “bigger” does not state an exact amount. That justification applies to an unspecified factor, not to a sentence containing 2. The proper reference for “make Box bigger” must preserve the direction of change while leaving the exact amount open. An executor may choose a documented default later; the reader should not be judged on that aesthetic choice.

Three other distinctions that must not disappear

First, node identity matters. If one request creates A and another creates B, a later reference to the first creation and a reference to the second creation are different graph edges. bench-canon.js currently represents both non-mention references as $new. The reader need not resolve an ambiguous pronoun, but when it emits a definite reference it must retain which node it points to.

Second, request order can carry meaning. For “Make Box red. Then make Box blue”, reversing the two operations changes the instruction sequence. With PAIR=value, matching favors the corresponding argument values and can pair the reversed red and blue outputs back to their gold counterparts. A direct probe counted both operations as right. The default order-based matcher is different; this criticism specifically concerns the value-based path used in confidence collection.

Third, the canonicalizer lowercases every scalar string. Case-insensitive matching may be appropriate for an identifier under this engine’s naming rules. It is not appropriate for text copied into a label: “API” and “api” are different requested literals. This is a separate code-level loss, not a measured current model error rate.

Make equivalence a small, explicit contract

Parse SOP into nodes and typed arguments before comparing it. Node IDs may be renamed consistently: @a and @b are equivalent labels if every reference follows the same renaming. Two different creation nodes must remain distinct. Keep exact literal strings, signed numbers and stated factors. Preserve operation order and dependencies whenever the sentence makes them meaningful.

Some equivalences are legitimate. Reordering the keys on one wire does not change its meaning. A symmetric operation such as swapping A and B may admit two orders for the pair. These cases should be listed by operation and supported by the symbolic semantics, not by a broad “ignore order” rule. Separate independent operations can be matched without requiring identical serialization; repeated edits of the same target cannot be treated as an unordered bag.

The acceptance checks follow directly: 2 must differ from 0.5; a reference to A must differ from one to B; “API” must differ from “api”; the two recoloring sequences must differ. Consistent renaming of internal wire IDs and reordering argument keys must still pass. A final-drawing replay can illustrate consequences, but the reader score should already detect these frame differences before execution.
