Engineering review / Text → SOP frame → symbolic execution

Does the SOP frame say what the text says?

The technology should understand a request well enough to hand its intent to an agent or a symbolic executor. Its responsibility is a faithful semantic frame: preserve what is stated, identify what remains unresolved, and avoid invented actions or values.

The boundary we are trying to build

For “Make Box red”, the reader should return the operation set, the target expression Box and color red. The symbolic system checks that Box exists and calls the operation. The reader must not add shape=circle. It must also not answer a count question by guessing a number: it hands over the query, and the symbolic system computes the answer.

@c1 command action=set target=Box color=red

For “Move it 20 px left”, the reader can preserve move, 20 px, left and the unresolved reference “it”. It does not need to resolve that pronoun. The crucial distinction is between a faithfully represented reference, an unread field reported as uncertain, and a concrete value asserted without evidence. The last is the false certainty this project should prevent.

This review now follows that boundary. It distinguishes reader errors from target-conversion losses, context-resolution decisions and execution defects. The drawing demo is a useful test bench; its final picture is not the definition of text understanding.

Start with what the score actually measures

The current main evaluation compares predicted SOP nodes with annotated types and arguments. That is the right level in principle. However, its canonicalizer and matcher can erase differences, and its field check can accept an invented argument. The score is deterministic but does not yet establish complete semantic fidelity.

Read the evaluation walkthrough: one request through the actual code, where judgment enters the annotation, which normalizations are legitimate, which ones lose meaning, and the proposed frame-level evaluator before context resolution.

The new Expected result tab in the demo is a separate aid: it shows the request, saved reference SOP and the drawing obtained by replaying it in an isolated engine. It helps inspect the intended result. It is not a model score, and its layout defaults or resolved scene context are not extra responsibilities imposed on the language reader.

Nine concrete failure points

Each page follows a request, shows the intended SOP where useful, locates the first loss in code, and describes the correction with an acceptance condition. Established code behavior is separated from unmeasured model-performance effects.

9 of 9 problems shown

01

An extra SOP argument is an extra assertion about the request.

The reader must preserve what the person said. Returning the requested color does not make the frame correct if it also asserts an unrequested shape change.

Measurement
02

The evaluator removes distinctions that a symbolic program needs.

Normalization is useful for harmless differences in notation. It becomes a bug when it removes an explicit amount, an entity identity, literal text or a dependency between operations.

Measurement
03

The training target sometimes loses part of the intended frame.

Before judging the learning algorithm, check whether the annotated meaning survives conversion into the model’s training format.

Data
04

SOP-BERT cannot emit fields that its output layout does not contain.

The fine-tuned encoder may recognize the words, but the exported reader still needs an output for every semantic field the text states.

Data
05

The pipeline must not turn lost information into a complete-looking frame.

A sign, a quoted label, one coordinate or unread text can be lost mechanically. A symbolic executor cannot recover the user’s original intent from a frame that hides that loss.

Representation
06

A reader comparison also compares its training data unless the data is held fixed.

The world, its cutters and SOP-BERT are trained from different declared message sets. That can affect which constructions they recognize before any architectural difference is measured.

Data
07

A wrong final frame does not tell us which VSS step caused it.

The useful engineering question is where the intended argument was first lost or changed: input preparation, target conversion, vector prediction or SOP assembly.

Representation
08

Confidence must estimate whether the SOP frame is faithful.

A confidence number is useful only if its right/wrong labels mean “this is what the text said”, and if unresolved references are not confused with false assertions.

Measurement
09

A failed export check or a stale cache can invalidate the model comparison.

Even a sound formalization model is not useful if the browser runs different weights, or the report silently reuses readings from an older build.

Engineering

What to experiment with after the contract is faithful

Future experiments, one by one covers all 12 proposals and subproposals: the failure each could address, what is underspecified or stale, and a controlled comparison that could answer the question.

VSS and SOP-BERT: limits and alternatives explains two concrete impossibility cases in the current interfaces, separates them from unproven model-capacity claims, and proposes partial frames, multi-event structures, symbolic checks and clarification as alternatives to test.

I would first repair semantic scoring and annotation/output round trips. Then compare model or data changes at the same rate of confident false frames, and retain the repository’s execution-risk and cost score as a separate full-system measure. A useful partial reader is preferable to a complete-looking invented interpretation.

What this review establishes

The inspected baseline is VSS-ALL with nine *8 worlds and SOP-BERT BERT-ALL, job 071. Earlier result documents are explicitly historical. Direct probes test scoring and conversion behavior with supplied inputs; they do not measure how often a trained model produces those errors. No new model training or full reader benchmark was run for this documentation.

The reference-output UI has separate engineering checks, including replay of all saved example programs. Successful replay means those programs are accepted by the engine; it does not prove every annotation is the only faithful interpretation. The page on evaluation explains how annotation uncertainty should be handled.

Terms used in these pages

Semantic frame
The operation or question and its argument values, references and unresolved parts: the meaning passed to the symbolic consumer.
SOP Lang
The syntax used to write that frame. A valid SOP program can still express the wrong intent.
Gold / reference
An annotated expected interpretation. It is reviewable data, not an infallible truth or a model prediction.
Role / argument
A named field such as target, color, width, distance or anchor.
Unresolved reference
An expression whose role is understood but whose concrete referent still needs context, for example “it”.
Round trip
Annotation → training/output format → SOP. This checks information preservation before testing a model’s predictions.
World / front
A VSS world handles a group of actions. Its front prepares text and learned word/category mappings before vector composition.
Coverage and risk
How much requested meaning is faithfully supplied, alongside how often a confident supplied frame is false. Execution coverage/risk is reported separately after resolution.
Calibration
Fitting confidence and selecting thresholds using the declared out-of-fold or held-out procedure.
Executor defaults
Choices made after reading when the user left a detail open, such as a default size. They must not be presented as text-derived values.
